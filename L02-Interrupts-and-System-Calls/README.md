# Lecture 2 — Interrupts & System Calls

## 1. Computer Organization (just enough)

To execute a program — a sequence of instructions plus data — you need:

1. **Main memory** — where instructions and data live.
2. **System bus** — moves instructions/data between memory and the processor.
3. **Processor (CPU)** — actually executes instructions.

### The processor

- Runs the **fetch → decode → execute** cycle repeatedly. Modern CPUs **pipeline** these stages (fetch the next instruction while decoding the current one while executing the previous one).
- **Word**: the largest unit the CPU operates on at once (32-bit CPU → 32-bit word; 64-bit → 64-bit).
- The instruction set is CPU-specific. Some instructions are **privileged** — only available in *supervisor mode*, not *user mode* (e.g. "disable interrupts"). Executing one in user mode is an error.
- **Registers**: tiny, very fast storage inside the CPU holding key variables, temporaries, and control info like the **program counter** (address of the next instruction) and **instruction register**. Managing them across programs is partly the OS's job.

## 2. Interrupts

### Why they exist

The CPU often needs data that takes a variable (and often huge) amount of time to arrive. Analogy: cache = book on your office shelf; disk = walking to Ottawa to get it. While waiting, the CPU should do *something else*. Two ways to find out when the data is ready:

- **Polling** — keep checking "is it here yet?" Wasteful: how often do you check, and how much time goes into checking?
- **Interrupts** — get *notified* when it arrives (the courier knocks on your door). You stop what you're doing, deal with it, then carry on.

The main purpose of interrupts is **improving processor utilization** — the fraction of time the CPU is doing useful work.

### Sources of interrupts

| Source | Example |
|--------|---------|
| **Program** | Division by zero, invalid memory access |
| **Timer** | A timer in the processor expires (e.g. updating the system clock, time-slicing) |
| **I/O** | A device controller signals an operation completed (or failed), e.g. disk read finished |
| **Hardware failure** | Power failure, memory parity error |

### Handling an interrupt

Like a professor answering a raised hand:

1. **Pause** execution.
2. **Save state** — remember exactly where you were.
3. **Handle** the interrupt (run the interrupt handler).
4. **Restore state** and resume as if nothing happened.

The **OS** is responsible for saving the interrupted program's state, running the handler, and restoring the state.

**Saving/restoring state** concretely means saving the CPU **registers** (program counter, instruction register, general registers...) by **pushing them onto the stack**, then popping them back into the registers afterwards.

### Disabling interrupts and priorities

- Sometimes an interruption at the wrong moment would be harmful, so interrupts can be **disabled** ("save your questions for the end of the lecture"). Pending interrupts are handled once they are re-enabled.
- Interrupts have **priorities**: if several are pending, the highest priority is handled first.

### Multiple interrupts

- **Sequential handling** — the handler disables interrupts while it runs; a second interrupt waits until the first is done.
- **Nested handling** — a higher-priority interrupt can interrupt a lower-priority handler.
- Systems often combine them: e.g. a low-priority handler is preempted by a high-priority one; if a medium-priority interrupt arrives during the high-priority handler, the high one finishes first, then the medium one runs, then the low one resumes.

### Multiprogramming

Since the interrupted program's state is saved, the OS doesn't have to resume *that same program* — it can run another one. Choosing which program runs next is **scheduling**, mostly out of the application programmer's control.

## 3. Traps (software interrupts)

A **trap** (or **exception**) is an interrupt generated by software. Two causes:

1. **An error** — invalid instruction, divide by zero. On desktop OSes this is usually delivered to the offending program and is often fatal (an unhandled exception).
2. **An intentional request from a user program** — this is how a program gets the OS's attention. While your program runs, the OS is effectively "asleep"; a trap wakes it so it can do something on your behalf.

## 4. User Mode vs. Kernel Mode

- **User mode**: restricted — privileged instructions are forbidden.
- **Supervisor/kernel mode**: everything allowed. Even "simple" things like reading from disk or writing to the console need privileged instructions, so they **always involve the OS**.
- The CPU tracks the current mode with a **mode bit**.
  - At boot → kernel mode (the OS is loading).
  - User programs always start in user mode.
  - Trap/interrupt → switch to kernel mode; OS does its work; switch back to user mode before resuming the program.

### Why dual mode?

Protection — the same reason we have user vs. admin accounts. Example: two programs reading the same disk. The OS makes Program 2 wait its turn. Without an enforcer, you'd rely on every program author to play nice, and eventually someone would cancel another program's request to jump the queue.

**Trade-off**: switching modes costs instructions and time; running everything in kernel mode would be faster. The security and integrity benefits are judged worth the overhead.

## 5. System Calls

A **system call** looks like a normal function call from your code, but it transitions into the OS to perform a privileged operation.

### Example: `read`

```c
ssize_t read( int file_descriptor, void *buffer, size_t count );
```

1. `file_descriptor` — which file (an `int` obtained earlier from `open`).
2. `buffer` — where in *your* memory to put the data.
3. `count` — maximum number of bytes to read.

Returns the number of bytes actually read: normally `count`, **fewer** near the end of the file, **0 at end-of-file**, **-1 on error** (and `errno` is set).

**Reading documentation is a core skill.** Search "`man 2 read`" or use man7.org / linux.die.net to learn parameters, return values, and error codes. (On Linux, `man 2 <name>` = system calls, `man 3 <name>` = C library functions.)

### A complete program: print a file

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>   /* read, close */
#include <string.h>   /* memset */
#include <fcntl.h>    /* open, O_RDONLY */

void readfile( int fd );

int main( int argc, char **argv ) {
    if ( argc != 2 ) {
        printf( "Usage: %s <filename>\n", argv[0] );
        return -1;
    }
    int fd = open( argv[1], O_RDONLY );
    if ( fd == -1 ) {
        printf( "Unable to open file! %s is invalid name?\n", argv[1] );
        return -1;
    }
    readfile( fd );
    close( fd );
    return 0;
}

void readfile( int fd ) {
    int buf_size = 256;
    char *buffer = malloc( buf_size );
    while ( 1 ) {
        memset( buffer, 0, buf_size );
        int bytes_read = read( fd, buffer, buf_size - 1 );  /* leave room for '\0' */
        if ( bytes_read == 0 ) {
            break;                                          /* end of file */
        }
        printf( "%s", buffer );
    }
    printf( "\nEnd of File.\n" );
    free( buffer );
}
```

Notice the `buf_size - 1` + `memset`: `read` does **not** null-terminate, so the code zeroes the buffer and leaves one byte free so `printf("%s")` always finds a terminator. (Also note the loop only checks for `0`; a robust version also handles `-1`.)

### What happens inside a system call — step by step

1. The user program **pushes the arguments** onto the stack (normal C calling).
2. The user program **calls** the system call wrapper (e.g. `read`) — an ordinary function call.
3. The wrapper puts the **system call number** (its identifier) in a designated place (usually a register).
4. The wrapper executes the **trap instruction** → switch to kernel mode, jump to the kernel's **trap handler** at a predefined address.
5. The OS examines the identifier in the designated location.
6. The OS runs the **system call handler** that matches that identifier (e.g. the file-read routine).
7. When done, control **exits the kernel** (back to user mode) and returns to the wrapper.
8. The wrapper **returns** to the user program with the result.

## New Functions Introduced

| Function | Header | Signature | Purpose |
|----------|--------|-----------|---------|
| `open` | `<fcntl.h>` | `int open( const char *path, int flags )` | Open a file and return a **file descriptor** (small int), or `-1` on error. `flags` e.g. `O_RDONLY`, `O_WRONLY`, `O_RDWR`. |
| `read` | `<unistd.h>` | `ssize_t read( int fd, void *buf, size_t count )` | System call: read up to `count` bytes into `buf`. Returns bytes read, `0` at EOF, `-1` on error. |
| `close` | `<unistd.h>` | `int close( int fd )` | Release a file descriptor. |
| `O_RDONLY` | `<fcntl.h>` | constant | Flag for `open`: read-only. |

Related (not formally introduced here but used with these exercises): `write( int fd, const void *buf, size_t n )` from `<unistd.h>` — the mirror of `read`; `STDIN_FILENO` (0), `STDOUT_FILENO` (1), `STDERR_FILENO` (2); `perror`/`strerror` for printing `errno` messages.
